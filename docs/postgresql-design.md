# PostgreSQL 与 pgvector 全量替换设计

日期：2026-11-15。状态：实施与验证完成；使用全新 PostgreSQL 数据库，旧数据保留但不导入。

## 已确认的目标

后端所有数据库存储统一使用 PostgreSQL，向量存储使用 pgvector。用户选择全新的空数据库，不导入现有 SQLite、Chroma 数据。旧数据文件不删除。保持 HTTP API、权限、流式事件、引用和前端功能契约。

## 方案与选择

采用单一路径切换：通过既有仓储端口接入 PostgreSQL，替换原适配器和组合根默认装配。业务和向量数据由同一个 PostgreSQL 实例管理。用户已明确要求全部替换，因此不提供长期 SQLite/Chroma 双后端模式，不引入双写。

驱动拟采用 psycopg 3 与 psycopg_pool；向量使用 pgvector 官方 Python 适配；LangGraph 使用官方 langgraph-checkpoint-postgres。保留显式 SQL 和现有领域模型，不额外引入 ORM。

## 当前环境事实

- Windows 本机 PostgreSQL 18 服务已运行；Docker CLI 存在，但守护进程未连接。优先复用本机服务。
- 2026-11-15 已使用本地 DATABASE_URL 验证：PostgreSQL 18.7、pgvector 0.8.7 已启用，目标库用户表为零，具备创建 schema 权限。连接凭据不写入文档。
- 当前 qwen3-embedding:4b 的模型信息报告输出维度为 2560。
- 当前后端涉及多份 SQLite 存储，Chroma 还承担文本块、元数据及文档列表事实来源；替换范围不只是向量查询。

## 替换范围

| 范围 | PostgreSQL 中的内容 |
| --- | --- |
| 认证 | 用户、密码哈希、会话摘要、登录限流记录 |
| 会话 | 正式对话、轮次、引用、反馈、分享及分页查询 |
| LangGraph | 官方 PostgreSQL checkpoint 表与线程清理 |
| 知识库 | 目录、生命周期、发布状态、删除计划及恢复状态 |
| 入库 | 持久队列、任务租约、栅栏标识和进度 |
| 文档及向量 | 文本块、原有元数据、collection 元数据、embedding |
| 追踪及管理查询 | 模型调用、耗时、成本、查询、引用统计和问题洞察 |
| 评估 | 独立评估向量集合、lane 运行清单、观测记录和评分检查点 |

评估 JSON/JSONL 报告、上传原始文件和普通日志属于文件产物，继续保留在文件系统；不是另一套数据库。BM25 保留现有算法，从 PostgreSQL 文本块构建内存索引。

## 数据库与配置

建议建立专用的新应用数据库，应用与评估数据使用明确隔离的 schema/命名空间；测试使用独立测试数据库。实际数据库名称由实施时结合本机情况确定，不连接或清空其他应用数据库。

增加 DATABASE_URL、TEST_DATABASE_URL 等集中配置。凭据只保存在本地 .env/环境变量，不写入源码、日志或文档。生产配置删除 SQLite 路径和 Chroma 路径的依赖，评估隔离验证改为 PostgreSQL 数据库/schema/集合身份验证。

提供可重复执行、带版本记录的数据库迁移命令和运行说明，串行管理建表与升级。运行进程不并发随意改表。LangGraph 官方 setup 同样纳入初始化步骤。pgvector 扩展由有权限的数据库管理员安装/启用；应用日常访问使用所需的最小权限。

## 向量及文本块

实现既有 VectorStoreReader/Writer/Admin 和知识内容读取端口。必须同时覆盖查询、批量写入、文档删除、文本块分页、文档头信息、计数、collection 元数据和清理操作。

保存完整精度的 vector 列，按集合记录并校验维度（当前模型为 2560），保持 cosine 距离和现有评分语义。当前规模先采用精确近邻查询，在 SQL 中先约束知识库、集合和未发布/排除文档，再计算距离并取 Top-K。不能通过先全库取 Top-K 再过滤模拟范围检索。

当前维度超过 pgvector 普通 vector HNSW 索引的 2000 维上限，所以初版不直接创建该索引，也不擅自截断维度或改变 embedding 模型。规模扩大时可另外评估 halfvec 表达式索引及完整向量重排；不作为本次实现的前置条件。

每个 collection 记录模型身份与维度，写入和查询校验维度及模型不混用。不同模型或维度必须使用独立集合，并通过重新入库建立向量。

## 事务、并发及生命周期

- 保持参数化 SQL，明确将 SQLite 占位符、JSON 操作、INSERT OR IGNORE、PRAGMA、ATTACH 等改为 PostgreSQL 语义。
- 认证限流、任务容量与租约竞争必须通过数据库事务、锁及约束保证；不能只用进程内锁。
- 队列抢占采用行锁与 SKIP LOCKED，保留租约超时、续租、取消及过期 worker 不得发布的栅栏规则。
- SKIP LOCKED 只处理任务抢占。队列容量检查与插入必须共用数据库容量控制行或事务咨询锁；入队、发布及删除冻结共用知识库行锁，并规定统一锁顺序，防止容量超卖及删除后仍发布。
- 文件锁中承担跨进程数据库写保护的部分改为 PostgreSQL 事务锁/咨询锁；文件删除仍需保留现有补偿和恢复语义。
- 同库读查询移除 SQLite ATTACH；保持读一致性、用户归属和管理员权限规则。
- 连接池由应用容器持有并幂等关闭；检查点连接按官方实现的事务和 autocommit 要求管理。
- 文档发布与删除跨文件系统的边界仍采用明确状态及补偿，不能声称与数据库天然构成原子事务。

## 测试与验收

1. 测试不依赖用户现有数据库数据；测试库保护应拒绝生产/开发数据库误用。
2. 所有原 SQLite/Chroma 直接实例化测试改为覆盖 PostgreSQL 适配器，不能通过保留旧实现或整体跳过掩盖迁移遗漏。
3. 保留纯单元测试的离线边界；数据库测试仅允许显式测试实例，真实模型测试继续单独开启。
   增加独立数据库测试 marker/fixture，仅放行 TEST_DATABASE_URL 对应目标，不借用会全面放行网络的 integration 标记。按测试/worker 隔离 schema，官方 PostgresSaver 的 search_path 同样受隔离和清理规则约束。
4. 检查并发入库抢占、租约栅栏、容量限制、认证限流、会话分页及归属、删除恢复、取消与关闭。
5. 检查真实 2560 维向量、cosine 排序、范围过滤、未发布文档排除和 collection 隔离。
6. 检查 LangGraph 重启后恢复、线程删除及评估恢复不串运行。
7. 全量后端测试、前端测试和 live 构建通过；真实登录、上传、向量化、混合检索、重排序、带引用流式问答及多轮保存通过。
8. 重启应用再核验数据；生产及评估运行路径均不再打开 SQLite 或 Chroma。

## 建议实施顺序

先确定本机专用数据库连接和扩展，再建立 schema/迁移与数据库测试基础；随后替换业务仓储、向量及文本内容仓储、检查点与评估存储；最后切换配置和默认装配、移除旧依赖、更新文档并完成全链路验证。
