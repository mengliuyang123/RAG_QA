# 检索评估：改动前后对比

## 范围与方法

- **数据**：`evaluation/corpus_manifest.json` 中 15 篇语料有 5 篇本地缺失（`langchain_knowledge_base.md`、`langchain_quickstart.md`、`langgraph_agentic_rag.md`、`langgraph_persistence.md`、`langgraph_quickstart.md`），因此只用其余 10 篇；`qa_dataset.json` 的 50 题中去掉依赖缺失语料的 21 题，剩 29 题。结果不能与以往 50 题的报告直接比较。
- **语料哈希**：本机 `core.autocrlf=true`，检出后的语料是 CRLF，与清单 sha256 不符；评估使用转回 LF 的临时副本，全部 10 篇哈希一致。仓库文件未改。
- **只评检索**：复用 `evaluation/runtime.py` 的建索引流程（改动后按 Markdown 标题拆章节、父子分块、带结构前缀向量化），对每题用三种策略取 `top_k=5`，统计期望来源文件的排名。不调用生成模型和裁判模型，**回答质量未评估**。
- **模型**：Embedding `qwen3-embedding:4b`（本机 Ollama），重排 `bge-reranker-v2-m3`（本机 llama.cpp）。没有产生费用。
- **改动前**：提交 `52bb974` 的代码；**改动后**：本变更的工作区代码。默认参数：`CHUNK_SIZE=500`、`CHUNK_OVERLAP=50`、`PARENT_CHUNK_SIZE=1500`。

## 结论

- **命中率没有下降**，vector 和 hybrid 各有 1 题的期望来源从第 2 名升到第 1 名。29 题大多已经接近满分，这个数据集区分度有限。
- **交给模型的上下文约为原来的 2.7 倍**（约 2000 字 → 约 5500 字），与 design 中“最多约 3 倍”的预估一致，生成的 Token 费用会相应上升。
- 平均来源文件数略降：父块合并后，前 5 条证据更集中在同一文档的不同章节。
- **未验证**：回答质量（RAGAS 等裁判指标）和真实 Token 费用。需要补齐缺失语料后，用完整的 `evaluation/run_eval.py --full` 评估。

# 完整评估：改动后的回答质量

## 运行信息

- **Run ID**：`20261118T090647Z-39acb214`（报告：`evaluation/results/runs/20261118T090647Z-39acb214.md`）。代码为提交 `39acb21` 加未提交的工作区改动：10 篇 / 29 题数据集、评估记录改用父块上下文、内容审核失败的处理。
- **命令**：`uv run --group eval python -m evaluation.run_eval --full`。本地 QA 29 题 × 3 种策略 = 87 条，RGB 中文子集 150 条。
- **模型**：生成 `qwen3.8-flash`（远程计费），Embedding `qwen3-embedding:4b`，重排 `bge-reranker-v2-m3`，裁判 `gemma4:12b`（本机 Ollama，上下文窗口 16384）。

## 运行中发现并修正的问题

1. **RAGAS 拿到的上下文和生成模型看到的不一致**：评估记录存的是命中的子块原文，约 1600 字，而生成模型看到的是父块上下文，约 5500 字。这会让忠实度系统性偏低，`local-028` 还因此让裁判反复改判，直到输出被截断。现在 `QueryService.evaluate_query` 改为记录生成模型实际看到的上下文。第一轮运行（`20261117T203825Z-39acb214`）因此作废。
2. **上游内容审核拒绝**：RGB `zh_refine:267` 的 passage 被生成服务以 `data_inspection_failed` 拒绝，重试也不会通过。现在这类 case 记为 `content_filtered` 失败并继续，不计入准确率，各分组单独给出 `failed_count`。完整报告只允许这一种失败。本轮共有 3 条：267 的噪声 0.4、0.8 和拒答各 1 条。
3. **偶发的输出循环**：RGB `zh_refine:299`（噪声 0）有一次回答写满了 4096 Token 上限。单独重放同样的输入，94 Token 就正常答对了，续跑时重新生成即可，没有改代码。
